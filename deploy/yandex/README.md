# kb-сервер в Yandex Cloud

`kbengine serve --tenants s3://<бакет>` в Serverless Container: у каждого человека своя
база и свои финансы под `users/<id>/`, вход по личному токену. Выкатка и проверка живого —
`deploy.sh`:

```sh
BUCKET=<бакет> YC=~/yandex-cloud/bin/yc deploy/yandex/deploy.sh           # выкатить текущий коммит
BUCKET=<бакет> YC=~/yandex-cloud/bin/yc deploy/yandex/deploy.sh --verify  # только проверить
```

Скрипт повторяемый: создает недостающее (ключ, сервисный аккаунт, реестр, контейнер),
приводит защиту существующего к описанию (защита ключа от удаления, версии и закрытый
анонимный доступ бакета, ACL) и выкатывает новую ревизию. Из дерева с правками или новыми
файлами не выкатывает. `PROBE_TOKEN_FILE=<файл со своим токеном>` добавляет к `--verify`
положительную проверку: вход по `X-KB-Token` отвечает 200.
`KB_ANDROID_APP=<пакет:отпечаток>` (печатает `just android`) кладет приложение Android в
окружение контейнера: сервер отдает `/.well-known/assetlinks.json`, DVK на телефоне
открывается во весь экран, а `--verify` проверяет и его, и страницу телефона `/m/`.
`KB_PUSH_CONTACT=mailto:<адрес>` включает push телефонам («Компьютер ответил»): ключ VAPID
сервер создает сам при первом вызове и хранит в бакете (`auth/vapid.json`, рядом с токенами
телефонов); с `PROBE_TOKEN_FILE` `--verify` проверяет, что ключ отдается. Смена или потеря
ключа отменяет подписки — телефоны включают уведомления заново.

## Как защищены данные

Данные людей — их базы знаний и финансы; токен открывает и то, и другое. Слои, от
внешнего к внутреннему:

| Слой | Что | Почему так |
|---|---|---|
| Вход | HTTPS-адрес контейнера открыт, пускает только личный токен приложения (192 бита); сервер хранит SHA-256, сравнивает за постоянное время, чужой токен — 401, чужая база — 404 | IAM на входе потребовал бы облачный аккаунт каждому человеку и не добавил бы защиты данных: токен не подобрать |
| Изоляция | на каждого человека свой обработчик, `<id>` берется только из токена | фильтра «не показывать чужое» нет нигде, потому что чужого в обработчике нет |
| Хранилище | бакет приватный, анонимный доступ закрыт; ACL — только сервисный аккаунт `kb-server`, только чтение и запись; ни у одного сервисного аккаунта нет ролей на каталог или облако (`--verify` проверяет); доступ есть еще у владельца облака | роль на каталог открыла бы и любой будущий бакет каталога |
| Версии | у бакета версии, старые хранятся 30 дней | ошибка записи или украденный токен не стирают данные насовсем |
| Сроки | правила жизненного цикла задает `deploy.sh` целиком: версии — 30 дней, `test/` — день, `mailfiles/` (голос и вложения телефона, #658) — 2 дня, их версии — день; `--verify` проверяет `mailfiles/` | окно удаляет забранный файл само, но не забранное копилось бы без конца |
| Шифрование | бакет шифруется ключом KMS `kb-bucket` по умолчанию, право на ключ — у `kb-server`; у ключа защита от удаления, ротация раз в год; `--verify` проверяет каждый объект вне `test/` | удаленный ключ — данные, которые не расшифровать ничем; шифрование по умолчанию не касается объектов, записанных до него |
| Контейнер | образ по digest, distroless, без root; секретов в окружении нет (бакет — через сервисный аккаунт и метаданные, ключ записи в Monium — из Lockbox); точка метаданных AWS v1 закрыта | тег можно перевесить, digest — нет |
| Счет | 1 экземпляр и 8 одновременных запросов на зону доступности, зон три — не больше 3 и 24 | чужие запросы без токена не превращаются в счет |
| Логи | сервер не пишет журнал запросов, тела и токены не логируются; только ошибки; в Monium уходят строки с `Bearer`, `Api-Key`, `token=` уже с вычеркнутым значением | ключ записи в Monium лежит в Lockbox, не в окружении |

## Токены

- Выпуск: `kbengine users add --tenants s3://<бакет> --id <имя>` и ровно одно место:
  `--keychain <id источника>` — **только свой** токен, в Связку этого Мака (ее читают окно
  и агент); чужой — `--token-out <новый файл>` (0600), передать человеку и удалить.
- **В терминал токен не выводится никогда**: вывод терминала попадает в историю оболочки,
  журнал агента и переписку с моделью. Запускать `users add` в обычном Терминале, не через
  агента.
- На Маке токен живет только в Связке ключей; окно и `kbengine-mcp` читают его оттуда,
  по `http` на сетевой адрес не отправляют, перенаправлениям не следуют.
- Отзыв: `kbengine users revoke --tenants s3://<бакет> --id <имя>`; сервер узнает за минуту.
  Закрывает вход, телефоны и push; база остается.
- Область токена (#701, #703): `kbengine users add ... --scope read|append|write` и, для
  существующего человека, `kbengine users scope --id <имя> --scope read|append|write` (сервер
  узнает за минуту; `add` без `--scope` явно снимает старую запись). `read`: только чтение,
  любой метод кроме `GET`/`HEAD` (записи, финансы, ящик, телефоны) получает 403 до обработчика.
  `append`: чтение плюс добавление записи (`POST /api/entries`, ровно этот путь), без правки
  (`PATCH`), удаления, финансов и ящика; добавленное проходит ту же проверку и дедуп по адресу,
  что и `kbengine add`. Область лежит в `auth/scopes.json`, старый код этот файл не читает.
  Закрыто при сбое: файл областей, который не прочитать (сбой дольше 5 минут, битый, с
  неизвестным полем), значит «пишет никто, читают все», причина идет в журнал сервера.
  Ограничение начинает действовать за минуту (кэш `RefreshEvery`), при сбое чтения старый
  список живет до 5 минут. **Откат сервера на версию до #701 снимает ограничение: старый код
  `auth/scopes.json` не читает, и `read`/`append`-токены пишут. Перед откатом отзови такие
  токены: `users revoke`.** `POST /api/finances/export` для `read` и `append` дает 403 (выгрузка
  по `GET /api/finances/export.xlsx` работает). Для облачных сессий Claude Code (#546) выдавайте
  `read` или `append` отдельному арендатору без личных данных.
- Удаление человека целиком (#545): `kbengine users purge --tenants s3://<бакет> --id <имя>
  --confirm <имя>`: без `--yes` только показывает, что есть у этого имени (в реестре, телефоны,
  база), и ничего не меняет; с `--yes` закрывает вход, ждет 5 мин 10 с (`--wait`; дольше `MaxStale`: сбой чтения
  реестра держит на экземпляре старый список до 5 минут, а повтор команды ждет снова), затем
  удаляет `users/<имя>/` (база, финансы, журнал ящика), `mailfiles/users/<имя>/` и
  `auth/seen/<имя>.json` со **всеми версиями** объектов и метками удаления, и вторым проходом
  проверяет, что после удаления ничего не записано. Допустимы только префиксы одного человека
  (`blob.ValidPurgePrefix`). Ключ под префиксом, который через адрес выразить нельзя (`..` или пустой сегмент), пропускается
  и называется в ошибке: удалить его надо руками. Прерванная команда оставляет данные целыми,
  повтор безопасен.
  Оговорки: имя и хэш токена еще 30 дней лежат в старых версиях общих реестров `auth/*.json`;
  логи в Monium не удаляются. Проверено: файловое хранилище, модель версионного бакета и живой
  бакет (`TestLiveYandexPurge`, `TestLiveYandexPurgeLeavesNoVersionsOrMarkers`, токен владельца).

## Подключения в настройках

Правило для любого источника, который окно подключает своим ключом (kb-сервер сейчас,
сторонние сервисы потом): **секрет подключения живет только в Связке ключей на Маке, а на
сервере, когда понадобится, — в Lockbox.** Его не бывает в `config.json`, в каталоге, в
логах, в выгрузках Excel, в ответах API и MCP. Данные, которые сервис отдал нам, остаются
в базе человека и не уходят дальше приложения.

Оговорка честная: когда агент ищет по базе через MCP, найденные записи уходят модели —
так работает любой агент. Агент на Маке владельца ходит на сервер только с токеном
владельца, поэтому чужие базы ему недоступны.

## Мониторинг и алерты (06.11.2026)

Что работает:

- **Снаружи — UptimeRobot**, монитор «kb-сервер (Yandex Cloud) /healthz»: раз в 5 минут
  `GET /healthz` контейнера, сбой — письмо владельцу. Проверка из чужой сети видит и общий сбой
  Yandex Cloud. Telegram у UptimeRobot только на платных тарифах.
- **Изнутри — функция `kb-healthcheck`** (`healthcheck.sh`, код в `healthcheck/`): таймер
  `kb-healthcheck-5m` раз в 5 минут, вторая попытка перед алертом (холодный старт), алерт ботом
  владельца в Telegram. Токен бота — Lockbox `kb-alert-bot` (ключ `token`), его кладет владелец
  через stdin `yc lockbox secret create … --payload -`; скрипт и функция его не печатают, отказ
  Telegram назван полем `description`.

Что не работает и почему:

- **Таймер функции на паузе**: из Cloud Functions `api.telegram.org` недоступен (06.11 — `URLError`
  и на запрос с токеном, и на голый GET без него; с обычного компьютера отвечает). Обращение в
  поддержку отправлено. Вернуть: `yc serverless trigger resume --name kb-healthcheck-5m`.
- **Логи контейнера**: Cloud Logging с 22.10.2026 не подключается новым клиентам, а stdout
  контейнера в Monium сам не попадает (проверено 18.11: запрос по проекту за 2 дня пуст,
  квота записи 0,0%). Поэтому сервер отправляет ошибки сам (#440): с `KB_MONIUM_PROJECT` и
  секретом Lockbox `KB_MONIUM_SECRET` (ключ `api_key`, переменная `KB_MONIUM_API_KEY`) всё, что
  идет в stderr, уходит в Monium по OTLP на `ingest.monium.yandex.cloud` (запись 4,40 ₽ за ГБ,
  хранение бесплатно, 31 день). Без пары переменных отправка выключена, как и раньше. Сбой
  Monium сервер не замечает: очередь ограничена, лишнее отбрасывается, повторов нет; число
  недоставленных строк видно во второй строке `/healthz` (`log-dropped: N`), а при старте в
  Monium приходит маркер `logs are shipped to Monium`.

Проверка функции без алерта: `TG_CHAT=<id> deploy/yandex/healthcheck.sh --verify` — живой сервер,
`ok: true`, сообщений нет. Новая версия функции всегда получает тег `$latest`, даже с `--tags test`:
таймер вызывает именно ее, поэтому пробные версии ставить только с последующей выкаткой обратно.
