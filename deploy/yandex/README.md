# kb-сервер в Yandex Cloud

`kbengine serve --tenants s3://<бакет>` в Serverless Container: у каждого человека своя
база и свои финансы под `users/<id>/`, вход по личному токену. Выкатка и проверка живого —
`deploy.sh`:

```sh
BUCKET=<бакет> YC=~/yandex-cloud/bin/yc deploy/yandex/deploy.sh           # выкатить текущий коммит
BUCKET=<бакет> YC=~/yandex-cloud/bin/yc deploy/yandex/deploy.sh --verify  # только проверить
```

Скрипт повторяемый: создает недостающее (ключ, сервисный аккаунт, реестр, контейнер),
приводит защиту существующего к описанию (защита ключа от удаления, версии и закрытый
анонимный доступ бакета, ACL) и выкатывает новую ревизию. Из дерева с правками или новыми
файлами не выкатывает. `PROBE_TOKEN_FILE=<файл со своим токеном>` добавляет к `--verify`
положительную проверку: вход по `X-KB-Token` отвечает 200.

## Как защищены данные

Данные людей — их базы знаний и финансы; токен открывает и то, и другое. Слои, от
внешнего к внутреннему:

| Слой | Что | Почему так |
|---|---|---|
| Вход | HTTPS-адрес контейнера открыт, пускает только личный токен приложения (192 бита); сервер хранит SHA-256, сравнивает за постоянное время, чужой токен — 401, чужая база — 404 | IAM на входе потребовал бы облачный аккаунт каждому человеку и не добавил бы защиты данных: токен не подобрать |
| Изоляция | на каждого человека свой обработчик, `<id>` берется только из токена | фильтра «не показывать чужое» нет нигде, потому что чужого в обработчике нет |
| Хранилище | бакет приватный, анонимный доступ закрыт; ACL — только сервисный аккаунт `kb-server`, только чтение и запись; ни у одного сервисного аккаунта нет ролей на каталог или облако (`--verify` проверяет); доступ есть еще у владельца облака | роль на каталог открыла бы и любой будущий бакет каталога |
| Версии | у бакета версии, старые хранятся 30 дней | ошибка записи или украденный токен не стирают данные насовсем |
| Шифрование | бакет шифруется ключом KMS `kb-bucket` по умолчанию, право на ключ — у `kb-server`; у ключа защита от удаления, ротация раз в год; `--verify` проверяет каждый объект вне `test/` | удаленный ключ — данные, которые не расшифровать ничем; шифрование по умолчанию не касается объектов, записанных до него |
| Контейнер | образ по digest, distroless, без root; секретов в окружении нет (бакет — через сервисный аккаунт и метаданные); точка метаданных AWS v1 закрыта | тег можно перевесить, digest — нет |
| Счет | 1 экземпляр и 8 одновременных запросов на зону доступности, зон три — не больше 3 и 24 | чужие запросы без токена не превращаются в счет |
| Логи | сервер не пишет журнал запросов, тела и токены не логируются; только ошибки | |

## Токены

- Выпуск: `kbengine users add --tenants s3://<бакет> --id <имя>` и ровно одно место:
  `--keychain <id источника>` — **только свой** токен, в Связку этого Мака (ее читают окно
  и агент); чужой — `--token-out <новый файл>` (0600), передать человеку и удалить.
- **В терминал токен не выводится никогда**: вывод терминала попадает в историю оболочки,
  журнал агента и переписку с моделью. Запускать `users add` в обычном Терминале, не через
  агента.
- На Маке токен живет только в Связке ключей; окно и `kbengine-mcp` читают его оттуда,
  по `http` на сетевой адрес не отправляют, перенаправлениям не следуют.
- Отзыв: `kbengine users revoke --tenants s3://<бакет> --id <имя>`; сервер узнает за минуту.

## Подключения в настройках

Правило для любого источника, который окно подключает своим ключом (kb-сервер сейчас,
сторонние сервисы потом): **секрет подключения живет только в Связке ключей на Маке, а на
сервере, когда понадобится, — в Lockbox.** Его не бывает в `config.json`, в каталоге, в
логах, в выгрузках Excel, в ответах API и MCP. Данные, которые сервис отдал нам, остаются
в базе человека и не уходят дальше приложения.

Оговорка честная: когда агент ищет по базе через MCP, найденные записи уходят модели —
так работает любой агент. Агент на Маке владельца ходит на сервер только с токеном
владельца, поэтому чужие базы ему недоступны.
