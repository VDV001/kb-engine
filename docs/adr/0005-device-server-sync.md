# ADR-0005 — Устройство и kb-сервер: финансы очередью, база пачкой, контур у каждого свой

- Status: accepted
- Date: 2026-11-06
- Issue: #439

## Context

Окно DVK читает kb-сервер напрямую и локальной копии не держит: без сети источник
«нет связи», записать нельзя. Следующий шаг — окно начинает писать на сервер
(G3, #435), потом на сервер переезжают данные владельца (#434). До этого нужно
решить, когда устройству нужна живая связь с сервером, а когда хватает отправки
позже.

Ответы владельца, 06.11.2026:

- траты записываются **с Мака и с телефона**;
- **без интернета записывать бывает нужно** (самолет, плохая сеть, VPN не поднят);
- у каждого человека **свой закрытый контур**; общих данных сейчас нет, давать
  людям доступ к своему контуру — позже;
- **потерять запись хуже**, чем увидеть остаток на час старее.

Почему для финансов важны порядок и момент: расчетный остаток — это подтвержденное
число минус траты, записанные **после момента подтверждения**
(`domain.RecordedAt`). Момент записи берется из ULID ее id. Трата с телефона,
дошедшая на сервер позже подтверждения на Маке, считается правильно только если
ее момент — момент создания на телефоне, а не момент прихода на сервер.

## Decision

1. **Финансы — очередь на устройстве (outbox).** Запись принимается сразу и
   получает id (ULID) на устройстве, в момент создания. Без сети она ждет в очереди
   и уходит сама, когда сеть появится; человек ничего не нажимает. Порядок
   отправки — порядок создания.
2. **Записи базы — автовыгрузка пачкой**: раз в несколько минут и при закрытии
   окна. Свежесть тут не критична, а пачка проще очереди.
3. **Ручная «выгрузить за день» — не основной путь.** Ее забывают, и именно тогда
   теряются данные.
4. **Контур у каждого свой.** Сервер разводит людей (`serve --tenants`), устройство
   пишет только в контур своего токена. Доступ другого человека к своему контуру —
   отдельное решение потом; сейчас под него ничего не строится.

## Consequences

- **Требование к G3 (#435):** сервер принимает id записи от устройства и повтор
  того же id не задваивает (идемпотентная запись). Сейчас `POST
  /api/finances/transactions` id выдает сам — с очередью, которая повторяет
  отправку после обрыва, это давало бы дубли.
- **Момент — с устройства.** `RecordedAt` читает момент из ULID, выданного на
  устройстве, поэтому трата, записанная до подтверждения остатка на другом
  устройстве, не вычитается второй раз. Риск — сбитые часы устройства: момент
  выйдет неверным. Сервер может отказывать записи с моментом далеко в будущем;
  порог — при реализации.
- **Окно показывает очередь:** сколько записей ждут отправки и почему (нет сети,
  отказ сервера). Отказ сервера (например, правило валюты) не повторяется вечно —
  запись остается в очереди с причиной, человек решает.
- **Два устройства правят одну запись** — конфликт, как у `fin sync`: ни одна
  сторона молча не побеждает.
- Файлы папок на сервер не уходят; настройки окна остаются локальными.
- Офлайн-чтение (локальная копия базы для поиска без сети) этим решением не
  покрыто: окно по-прежнему читает сервер напрямую.
