# ADR-0008 — Двухуровневая память из коробки: горячий слой с потолком, холодный слой ищется

- Status: proposed (принят будет после ворот 3, см. «Критерии приёмки»)
- Date: 2026-11-09
- Issue: нет (запрос владельца голосом 08.11.2026)

## Context

Владелец просит базу знаний, в которой двухуровневая память есть сразу: человек получает скелет
горячего и холодного слоя, наполняет его руками или поручает агенту, и видно, что она дает.
Условия владельца (09.11.2026), по которым принимается решение:

1. экономим токены, а значит деньги;
2. в общей сессии то же качество без потерь примерно до 50% контекста модели (дальше контекст
   пухнет и уходят в новую сессию);
3. качество ответов не падает во всей сессии.

Замер собственной памяти владельца (08-09.11.2026, нижние оценки, токены по прокси `o200k_base`,
не токенайзеру Claude):

- горячий слой читается каждым ходом: проектный `CLAUDE.md` 39 796 знаков (12 825 токенов), индекс
  автопамяти 24 691 знак (8 482 токена), глобальный `CLAUDE.md` 8 054 знака (2 431 токен);
- в проектном `CLAUDE.md` раздел правил 18 253 знака, но правила в нем перемешаны с историями
  случаев; раздел «Проекты» (10 774 знака) это состояние проектов, то есть факты;
- холодный слой: 184 файла; за 51 сессию (09.10-06.11) открыто 14 разных, 23 чтения (считались
  только вызовы `Read`, поэтому нижняя оценка);
- журнал-хроника в той же памяти: 1,09 млн знаков, в корзину поиска ему не место.

Что показали замеры 09.11 (модель haiku, 184 записи, один прогон на вариант):

| Что сравнивали | Результат |
|---|---|
| Три способа найти запись: плоский индекс (A), темы с подиндексами (B), поиск по тексту записей (C), 16 лёгких вопросов | точность одинакова: 16 из 16 у всех, выдумок нет |
| Те же A и C, 10 сложных вопросов с ответом в тексте записи и 3 без ответа | A: 6 верно, 1 наполовину, 3 мимо; C: 9 верно, 1 мимо (спорный вопрос); без ответа 3 из 3 «НЕ НАЙДЕНО» у обоих |
| Токены на агента, вопрос с ответом | A ~96,6 тыс., B ~94 тыс., C ~86,2 тыс. (в них ~85-90 тыс. накладных расходов субагента) |
| Вопрос без ответа | A ~101 тыс., B ~109 тыс., C ~91 тыс. |
| Поиск записи без агента, 40 вопросов (20 перефразов без общих слов, 20 обычных), целевая запись в топ-3 | текст (BM25 с грубым стеммингом) 30; вектор (`bge-m3`) 39; смесь 1:1 36; смесь 1:3 37 |

Выводы: темы с подиндексами (B) ничего не дают, потому что агент открывает все подиндексы;
плоский индекс заставляет отвечать по одной строке и ошибаться на деталях из текста записи; на
перефразах текст уступает вектору заметно, на обычных вопросах разницы нет; равная смесь вектора
с текстом хуже одного вектора.

## Decision

1. **Два уровня загрузки, холодный слой из двух частей** в папке `dvk-memory/`:
   - `HOT.md` — горячий слой, читается в каждой сессии. Только то, что должно действовать без
     вопроса: правила, красные линии, текущий фокус, указание искать в холодном слое. Потолок
     задается при `init` (`--hot-limit`); значение по умолчанию 4 000 знаков подходит скелету для
     нового человека, но **не набору правил владельца** (одни глобальные правила 8 054 знака), для
     него потолок ищется замером;
   - `cold/` — долговечные факты, по файлу на факт, шапка `name`, `description`, `origin`;
   - `journal/` — handoffs и хроника: только дописывается, привязан к датам, из обычного поиска
     по умолчанию исключен.
   Третий (промежуточный) уровень не вводится: замер не показал, что он нужен агенту.
2. **Правило разнесения:** то, что обязано действовать без напоминания, живет в горячем слое; то,
   что отвечает на вопрос, живет в холодном. Правила нельзя выносить в холодный слой ради
   экономии (ворота 3).
3. **Поиск по холодному слою.** Текстовый поиск работает из коробки. Смысловой слой (индекс
   векторов с именем модели и размерностью, `search --build-index`) подключается, если задан
   эмбеддер (Ollama и `bge-m3`); с ним вектор идет первым, текст остается запасным и для точных
   идентификаторов. Без эмбеддера движок отвечает явной ошибкой `ErrNoSemanticLayer`, а не пустой
   выдачей. `INDEX.md` остается обзором для человека и в сессию не грузится; у него потолок
   размера, подиндексов по темам нет.
4. **«Кто я» — из портрета DVK (ADR-0007),** а не из отдельного текста: источник один, дублей нет.
5. **Запись агента ждет одобрения человека** (`origin: agent`, статус «ждёт»), в горячий слой
   переносит только человек.
6. **Команда** `kbengine memory init|check|add`. `check` возвращает код 1 при нарушении: потолок
   горячего слоя, запись без описания, запись без строки индекса, строка индекса без файла,
   слишком длинный крючок, индекс выше потолка, устаревший векторный индекс.

## Критерии приёмки (условия владельца)

| Критерий | Что подтверждено | Что нет |
|---|---|---|
| 1. Токены = деньги | Горячий слой в 1-4 тыс. токенов вместо ~20 тыс. на ход (по размеру разделов правил); поиск дешевле плоского индекса на ~11% на агента | Деньги в рублях не считались (зависят от цены и кэша); точный размер горячего слоя владельца не найден |
| 2. Без потерь до ~50% контекста | Меньший горячий слой оставляет больше места под работу | Качество против заполнения контекста не измерялось |
| 3. Качество ответов во всей сессии | Поиск фактов: вектор 39 из 40 в топ-3; агент на тексте 9 из 10 сложных | **Не измерено:** выполняет ли агент правила, если их вынести из горячего слоя; сквозная точность агента с векторным поиском; какой размер горячего слоя достаточен |

Статус остается `proposed` до прохождения ворот 3. План проверки: сравнить варианты горячего
слоя разного размера и состава (всё как сейчас; только правила; правила в сжатом виде) по трем
критериям: токены на старте и за сессию, точность и выполнение правил на заполнении контекста 0 и
50%, поиск фактов (текст, вектор, смесь) в связке с агентом.

## Consequences

- Скелет проходит собственную проверку сразу после `init` (есть тест).
- Агенту дан один способ дописывать память, не раздувая горячую.
- Для человека без Ollama остается текстовый поиск, качество на перефразах ниже (11 из 20 в
  первых пяти против 19 из 20 у вектора).

## Ceilings (ponytail)

- Замер: вопросы писал автор, 40 штук на одном корпусе из 184 записей, одна модель, один прогон на
  вариант; текстовый базис — самодельный BM25, а не поиск `kbengine` с синонимами и транслитом;
  масштаб в тысячи записей и точные идентификаторы не проверены.
- Полезность записей не измеряется. Путь вверх: счетчик обращений через MCP и отметка «помогло».
- Перенос между слоями ручной; автоматический кандидат по частоте обращений появится после
  счетчика.
- `add` пишет запись и строку индекса двумя шагами без транзакции; сбой между ними оставляет
  запись без строки, и `check` назовет ее `not-indexed`.
- Формат шапки читается самодельным разбором ключей, не полным YAML.
- Прототип в коде (`init|check|add`) пока реализует раскладку `HOT.md` и `cold/` без `journal/`,
  смыслового слоя, потолка индекса и статуса одобрения; остальное этого ADR еще не сделано.
