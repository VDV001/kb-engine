# ADR-0004 — Поле file означает ровно одну вещь

- Status: accepted
- Date: 2026-08-02

## Context

Поле `file` несло **два** значения одновременно, и это не было замечено при
проектировании — обнаружилось тупиком в обычной работе.

1. **Идентичность записи.** У стандарта, черновика статьи, модуля курса нет
   адреса в интернете. Файл — это и есть запись; команда `add` так и устроена:
   артефакт без файла отвергается.
2. **Указатель на заметки.** У чужой статьи в том же поле лежал путь к моему
   конспекту. Статья живёт по своему url, а файл говорит лишь «здесь мой разбор».

Столкновение стало видимым, когда понадобилось завести запись для сводного
конспекта: дедуп `add` ищет запись с таким же `file` и находил **статьи**,
которые этот конспект цитируют. Отказ был формально верным («один артефакт —
одна запись») и практически бессмысленным.

Замер живого каталога: 405 записей с `file`, из них **383 — чужие статьи**, то
есть второе значение встречалось в семнадцать раз чаще первого. Уникальных
конспектов, на которые они ссылались, — 100.

Попутно нашлось следствие того же смешения: `docs/` входит в список деревьев
собственных артефактов, поэтому **11 чужих статей движок считал собственными**
артефактами — с правом на семвер и участием в аудите версий.

## Decision

`file` означает ровно одно: **файл, которым запись является**.

Каждый конспект получает собственную запись в категории `writeups`, владеющую
своим файлом. Статья ссылается на неё через `related_ids` и `file` не несёт.
Перенос выполняет `kbengine migrate writeups` — план по умолчанию, запись по
`--apply`, идемпотентная.

Категория `writeups`, а не `creations`: разбор чужой статьи — не работа, которую
владелец публикует, и складывать полсотни заметок в портфолио из одиннадцати
материалов значило бы завести третье смешение вместо снятого второго.

## Consequences

**Живая база:** 333 записи переехали на ссылку, заведено 50 разборов, записей с
`file` стало 122 вместо 405. Каталог 1345 → 1395.

**Третье значение, найденное только на живых данных.** Первый прогон плана
предложил завести «разборы» из `notes/rescued/*` — а это тексты самих статей,
вытащенные из веб-архива после того, как оригиналы скрыли. Это тело записи, а не
заметка о ней. Признак точный и проверяемый: все сорок таких файлов лежат в
`notes/rescued/` и названы по id своей записи. Фикстура знала два значения из
трёх, поэтому тесты были зелёными и слепыми одновременно.

**Аудит пришлось учить новому.** После первого прогона на копии базы число
находок выросло с 2 до 37: каждый конспект, на который ссылаются три и больше
статей, попадал в кандидаты в канон. Быть процитированным всеми статьями,
которые разбираешь, — работа конспекта, а не признак каноничности; категория
`writeups` из кандидатов исключена.

**Дедуп поймал регрессию сразу после применения** — 1 группа превратилась в 7.
Заголовок записи-разбора берётся из первой строки файла, а конспекты в `docs/`
начинаются с заголовка **самой статьи**: шесть разборов получили имя того, что
разбирают. Переименованы в «Разбор: …». Разборы из `notes/` своих заголовков не
теряли, то есть дефект жил ровно в одной папке из двух.

**Цена.** В каталоге на 50 записей больше, и дашборд про категорию `writeups`
пока ничего не знает — они лежат в общем списке. Отдельный экран не сделан
намеренно: сначала стоит пожить с новой моделью.

## Alternatives considered

- **Дедуп `add` сравнивает только собственные артефакты.** Правка в одну функцию,
  закрывала конкретные 11 записей и оставляла оба значения в поле. Отклонено
  владельцем в пользу полного разведения.
- **Путь к разбору в текстовом поле `notes`.** Пять минут работы, но это текст, а
  не ссылка: `audit --check files` его не проверяет, и при переименовании
  конспекта связь тихо сгнила бы.
- **Отдельное поле-список файлов.** Чистая нормализация, но затрагивает домен,
  чтение и запись, API, дашборд и TUI ради задачи, которую решает уже
  существующий `related_ids`.
